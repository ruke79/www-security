# 実務活用ガイド (Use Cases)

> 🌐 [한국어](USE-CASES.md) · [English](USE-CASES.en.md) · [日本語](USE-CASES.ja.md)

本書は `api-security-lab` に実装された各メカニズム・脆弱性シナリオが
**実際の実務でどのように使われるか**をまとめたものです。各項目は「実務の状況 →
このプロジェクトの何が対応するか → よくある誤り」という形式です。

## 全体像: 1つのサービスとしてピースをつなぐ

架空の送金サービス **PayFoo** を例にとると、実装されたピースは次のように組み合わ
さります。

```
[모바일 앱] --(1) OIDC 로그인(Authorization Code + PKCE)--> [인가 서버]
     |                                                         |
     |  (2) access token(scope: balance.read) 발급 <-----------+
     |
     +--(3) Bearer 토큰으로 잔액 조회--> [API 게이트웨이] --(4) 토큰 introspection--> [인가 서버]
                                              |
                                              +--(5) 라우팅--> [잔액 서비스] --(6) mTLS/Client Credentials--> [정산 서비스]
```

1. **OIDC + PKCE (ch12/ch7)** — ユーザー認証、パブリッククライアントの保護
2. **Scope ベースの access token (ch7)** — パスワードではなく「権限」を委譲する
3. **Bearer トークン (ch7)** — API 呼び出しごとに付与
4. **Introspection/Revocation (ch9)** — ゲートウェイがトークンの有効性・失効を確認
5. **Rate Limiting (ch2)** — 料金プラン別のクォータ、濫用の遮断
6. **mTLS / Client Credentials (ch4/ch7)** — サービス間の信頼

つまり実務の認証・認可アーキテクチャはこれらのピースの**組み合わせ**であり、各ピース
をいつ選ぶかが設計力になります。

## 第1部. 防御メカニズムの実務活用

### OAuth 2.0 Authorization Code + PKCE (ch7)
- **実務の状況**: Web/モバイルアプリがユーザーに代わって API を呼び出す必要がある
  とき（ソーシャルログイン、自社 SSO）。PKCE はシークレットを隠せない SPA・モバイル
  の事実上の標準です。
- **適用例**: 「カカオ/Google でログイン」、バンキングアプリがユーザーに代わって口座
  API を呼び出す。
- **よくある誤り**: `redirect_uri` を緩くマッチング（部分一致を許可）→ トークンの窃取。
  パブリッククライアントに PKCE を適用しない。いまだに Implicit grant を使用（現在は
  非推奨）。

### Client Credentials (ch7)
- **実務の状況**: ユーザーを介さずサーバー↔サーバーが通信する（マイクロサービス、
  バッチ、cron）。
- **適用例**: 注文サービスが在庫サービスを呼び出す、夜間の精算バッチ。
- **よくある誤り**: 人間用トークンとサービス用トークンの scope を区別しない。client
  secret をコード/イメージにハードコーディングする。

### OIDC ID Token (ch12)
- **実務の状況**: シングルサインオン（SSO）と「このユーザーは誰か」の標準的な証明。
- **適用例**: 社内の複数システムに一度でログイン、ソーシャルログインのプロフィール
  受信。
- **よくある誤り**: ID token の `aud`/`iss`/`nonce`/`exp` の検証漏れ、ID token を API
  アクセストークンのように誤用する（ID token は「認証の証明」、access token は「認可」
  が原則）。

### mTLS (ch4)
- **実務の状況**: 金融/B2B API、サービスメッシュ内部の通信、パートナー企業専用の連携。
- **適用例**: オープンバンキング、Istio サイドカー間の通信、決済代行会社との連携。
- **よくある誤り**: **証明書の信頼＝管理者権限**と一括りにする（→ シナリオ4）。証明書
  失効（CRL/OCSP）を確認しない。証明書の有効期限監視がない。

### DPoP - sender-constrained token (ch8)
- **実務の状況**: トークンが窃取された際の再利用を防ぐべき高リスク領域（フィンテック、
  オープンバンキング）。
- **適用例**: パブリッククライアント（SPA）での bearer トークン窃取リスクの緩和。
- **よくある誤り**: `jti` の再送キャッシュを単一インスタンスのメモリだけに置く（分散
  環境で回避される）。proof の `htu`/`htm`/`ath` バインディングの検証を省略する。

### Token Introspection·Revocation (ch9)
- **実務の状況**: API ゲートウェイでの中央集約的なトークン検証、ログアウト/侵害時の
  即時無効化。
- **適用例**: Kong/APISIX などがリクエストごとに introspection、アカウント乗っ取り時に
  全トークンを失効。
- **よくある誤り**: 自己エンコード（JWT）トークンは**ローカル検証だけでは失効を反映
  できない** → 寿命を短く + refresh で補う必要がある。introspection エンドポイントを
  保護しない。

### UMA (ch10)
- **実務の状況**: ユーザーが自分のデータを第三者に**ポリシーに基づいて**共有する。
- **適用例**: マイデータ、ヘルスケアの同意共有、ドキュメント共有権限の委譲。
- **よくある誤り**: チケットの発行＝即アクセス許可として扱う（ポリシー評価の省略、
  → シナリオ7）。

### Federation / JWT·SAML Bearer (ch11)
- **実務の状況**: 買収・提携により外部組織のユーザーを信頼する必要があるとき。
- **適用例**: パートナー企業の従業員が自社 API にアクセス、企業間 SSO。
- **よくある誤り**: 外部 assertion の `iss`/`aud`/署名/有効期限の検証が不十分 → 身元の
  なりすまし（→ シナリオ6）。信頼対象（発行者）をホワイトリストで固定しない。

### JWT / JWS / JWE (ch13)
- **実務の状況**: ステートレス認証、サービス間のクレーム受け渡し、機密情報の暗号化
  転送。
- **適用例**: ゲートウェイが検証したユーザー情報を JWS で下位サービスに渡し、機密
  クレームは JWE で暗号化する。
- **よくある誤り**: `alg` を固定しない（→ シナリオ15）、弱い HMAC 鍵、「署名の後に
  暗号化」の順序違反、機密情報を署名のみで平文のまま露出する。

### Rate Limiting (ch2)
- **実務の状況**: API の商品化（料金プラン別クォータ）、総当たり・DDoS の緩和。
- **適用例**: 無料 100 回/日 vs 有料 無制限、ログイン試行の制限。
- **よくある誤り**: クライアントが操作可能なヘッダーで識別する（→ シナリオ1）、単一
  インスタンスのメモリカウンター（分散回避）。認証済みユーザーは IP ではなくユーザー
  ID を基準に併用する必要がある。

## 第2部. 脆弱性の実務的な意味（ペンテスト・セキュアコーディング）

lab（#8–17）は実際の侵害事故・バグバウンティで最も頻繁に出てくる項目です。

### IDOR / BOLA (#10) — OWASP API セキュリティ1位
- **どこで**: `/api/orders/{id}` 系のすべての参照/更新 API。
- **実務上の意味**: ログインは正常なのに**オブジェクトの所有権検証**を漏らし、他人の
  注文・診療記録・ドキュメントを閲覧してしまう。大規模な個人情報流出の定番の原因。
- **点検ポイント**: id を1ずつ増減させたり、別アカウントのリソース id でアクセスして
  みる。

### SQL インジェクション (#8)
- **どこで**: ログイン・検索・フィルタ・ソートのパラメータ。
- **実務上の意味**: 認証バイパス、DB 全体のダンプ。`sqlmap` 自動化ツールの主な標的。
- **点検ポイント**: `'`、`' OR '1'='1`、`UNION SELECT`、時間遅延（blind）ペイロード。

### SSRF (#12)
- **どこで**: 「URL を受け取ってプレビュー/取得/Webhook」する機能。
- **実務上の意味**: サーバーのみがアクセスできる内部ネットワーク・クラウドメタデータ
  の窃取。代表例が **Capital One（2019）** — SSRF で AWS メタデータの資格情報を取得し、
  1億件あまりが流出した事故のタイプ。
- **点検ポイント**: `http://169.254.169.254/`、`http://localhost:.../internal` などの
  内部アドレスを入れてみる。

### Mass Assignment (#11)
- **どこで**: 会員情報の修正、プロフィール更新。
- **実務上の意味**: リクエストボディに `{"role":"admin"}`・`{"isVerified":true}` を
  紛れ込ませて権限昇格。ORM にリクエストオブジェクトを丸ごとバインドする際に発生する。

### XSS (#9)
- **どこで**: 掲示板・コメント・検索結果・プロフィールなど、ユーザー入力が画面に表示
  される箇所。
- **実務上の意味**: セッションクッキーの窃取、管理者アカウントの乗っ取り、フィッシング、
  ワーム。

### OS Command Injection (#14)
- **どこで**: 管理ツール、ネットワーク診断（ping/nslookup）、ファイル変換・画像処理。
- **実務上の意味**: サーバーの完全乗っ取り（RCE）。シェルに入力を連結する際に発生する。

### Path Traversal (#13)
- **どこで**: ファイルのダウンロード/アップロード、テンプレート・リソースの読み込み。
- **実務上の意味**: `../` で設定ファイル・秘密鍵・`/etc/passwd` を流出させる。

### SSTI / 式インジェクション (#16)
- **どこで**: メール/レポートのテンプレート、ノーコード・数式入力機能。
- **実務上の意味**: サーバー側での式評価 → 情報露出・RCE。Spring なら SpEL、その他は
  Freemarker/Velocity/Jinja2 など。

### JWT alg:none · 弱い鍵 (#15)
- **どこで**: 検証ロジックを自前実装している場合。
- **実務上の意味**: 管理者トークンの偽造、認証の完全バイパス。「標準ライブラリ + alg
  固定 + 強い鍵」が原則。

### NoSQL インジェクション (#17)
- **どこで**: MongoDB ベースのログイン・検索。
- **実務上の意味**: `{"$ne":null}` のような演算子を注入し、パスワードなしでログインする。

## 第3部. このプロジェクトを実務に使う3つの方法

1. **開発者オンボーディング / セキュアコーディング教育**
   - 各 lab の「脆弱 vs 安全」エンドポイントを実際に呼び出して比較する。なぜ
     PreparedStatement・出力エンコード・所有権検証・入力型の強制が必要なのかを体感する。
   - 例: `search`（脆弱）と `search-safe`（安全）に同じペイロードを入れて結果を対照する。

2. **レッドチーム / 模擬ハッキング訓練**
   - Burp Suite・`sqlmap`・OWASP ZAP の練習用ターゲットとして使う。
   - 例: `sqlmap -u "http://localhost:19080/api/lab/sqli/search?name=x"` で UNION 自動
     抽出、ZAP スキャナで XSS/SSRF を検出。

3. **CI セキュリティ回帰テスト**
   - 「安全なエンドポイントは攻撃ペイロードを遮断しなければならない」を自動テスト化し、
     リファクタリング中に防御が壊れたらビルドを失敗させる。
   - 例: `' OR '1'='1` → `search-safe` は0件、`verify-secure` は alg:none を401で拒否
     するかを検証（本書の再現コマンドがそのままテストケースになる）。

## 核心的な教訓

- **認証（誰か）だけでは不十分で、認可（何ができるか）こそが本当の防御線**です。優れた
  OAuth/OIDC を付けても、IDOR (#10) のようにオブジェクト単位の権限を漏らせば崩れます
  （だから OWASP API 1位が BOLA なのです）。
- **セキュリティ機能を自前実装せず、検証済みの標準・ライブラリを使い、アルゴリズム・
  信頼対象を明示的に固定してください**（alg:none・弱い鍵・audience 未検証が繰り返される
  誤り）。
- **入力はデータとしてのみ扱ってください。** SQL・OS コマンド・HTML・式・クエリ文書の
  どこであれ、ユーザー入力が「コード/構造」になる瞬間にインジェクションになります。
  パラメータバインディング・出力エンコード・型の強制が共通の解決策です。

# 付録A. IDOR / BOLA 詳解

> 関連実装: [`lab/IdorLabController.java`](src/main/java/com/example/apisecurity/lab/IdorLabController.java)、
> シナリオ [#10](VULNERABILITY-SCENARIOS.md)

## A.1 BOLA vs BFLA — 何を見落としたか

OWASP API セキュリティでは、認可の欠陥が2種類に分けられます。

- **BOLA (Broken Object Level Authorization, API1)**: 「この**オブジェクト**（注文
  1002）にアクセスする権限があるか？」を見ない。→ 他人の注文を閲覧する。
- **BFLA (Broken Function Level Authorization, API5)**: 「この**機能**（管理者削除
  API）を呼び出す権限があるか？」を見ない。→ 一般ユーザーが管理者エンドポイントを
  呼び出す。

lab の `orders` の例は BOLA、ch2 の PDP(admin-resource) や ch3 のロールベースの制約は
BFLA の防御に該当します。**両方とも必要です** — エンドポイントへのアクセス権（BFLA）
があっても、その中で扱うオブジェクトの所有権（BOLA）を改めて確認する必要があります。

## A.2 よくある勘違い: 「UUID を使えば安全だ」

順次 ID（`1001, 1002`）を UUID に変えると**推測は難しくなりますが、脆弱性はそのまま**
です。IDOR の本質は「予測可能性」ではなく、**「アクセス時に認可検証をしていない」**こと
です。UUID はログ・リファラー・共有リンク・アプリ内部に露出するため、防御ではなく緩和策
にすぎません。（だからシナリオ #10 の安全なエンドポイントも id の形式とは無関係に
**所有権を検証**します。）

## A.3 どこで検証するか — コントローラではなくデータアクセス層

脆弱なコードはたいてい「照会したあと返す」です:

```java
// 취약: id로 찾아서 그냥 반환 (소유권 미확인)
Order o = orderRepository.findById(id);
return o;
```

3つの堅牢な防御パターン:

```java
// (1) 쿼리 자체에 소유자 조건을 박는다 - 가장 견고 (없으면 404)
Order o = orderRepository.findByIdAndOwner(id, currentUser)
        .orElseThrow(() -> new NotFoundException());

// (2) 메서드 보안으로 반환 객체를 사후 검증
@PostAuthorize("returnObject.owner == authentication.name")
public Order getOrder(String id) { ... }

// (3) 서비스 계층에서 명시적 소유권 확인 (lab의 orders-safe 방식)
if (!order.owner().equals(currentUser)) throw new ForbiddenException();
```

**推奨は (1)** です: 「なければ 404」なので、リソースの存在有無すら露出しません。
コントローラ1か所だけで防ぐと新しいエンドポイントを追加する際に漏れやすいので、
**リポジトリ/サービス層に所有権を押し込むこと**が実務では安全です。

## A.4 実践的な点検方法（ペンテスト）

1. アカウント A でログインしてリソースの一覧/詳細をキャプチャし、id を収集する。
2. アカウント B のトークンで **A の id にアクセス**してみる（順次なら ±1 fuzzing）。
3. Burp Suite の **Autorize / Auth Analyzer** 拡張で「低権限セッションで高権限
   リクエストを再生 → 応答が 200 か」を自動比較する。
4. 参照だけでなく、**更新/削除（PUT/DELETE）**とネストしたリソース
   (`/orders/1002/items`) も必ず確認する。

## A.5 lab で直接確認

```bash
# 취약: alice가 bob(1002)의 주문 열람
curl -s "http://localhost:19080/api/lab/idor/orders/1002?asUser=alice"
# 안전: 소유자 아니면 403
curl -s "http://localhost:19080/api/lab/idor/orders-safe/1002?asUser=alice"
```

> 実務の参考: 大規模な個人情報流出の相当数が BOLA に起因します。「ログインは済んで
> いるから安全だ」という勘違いが最も危険です — 認証とオブジェクト認可は別物です。

# 付録B. mTLS（相互 TLS）詳解

> 関連実装: [`config/MtlsSecurityConfig.java`](src/main/java/com/example/apisecurity/config/MtlsSecurityConfig.java)、
> [`ch4/Ch4Controller.java`](src/main/java/com/example/apisecurity/ch4/Ch4Controller.java)、
> シナリオ [#4](VULNERABILITY-SCENARIOS.md)

## B.1 一方向 TLS vs 相互 TLS

- **一方向 TLS（一般的な HTTPS）**: クライアントが**サーバー**の身元だけを検証する
  （サーバー証明書）。Web ブラウジングの基本。
- **相互 TLS（mTLS）**: ハンドシェイクで**サーバーもクライアントに証明書を要求**し、
  クライアントが秘密鍵で署名（`CertificateVerify`）して身元を証明する。双方が互いを
  検証します。

ハンドシェイクの観点（ch4 の要約）: サーバーの `CertificateRequest` → クライアントが
証明書チェーンを送信 → `CertificateVerify`（それまでのハンドシェイクメッセージを
クライアントの秘密鍵で署名）→ サーバーがクライアントの公開鍵で検証 + トラストストアの
信頼 CA でチェーンを検証。

## B.2 核心的な原則: 「信頼（truststore）≠ 認可（権限）」

シナリオ #4 の教訓は、実務で最も頻繁に破られる箇所です。mTLS が保証するのは
**「この証明書は我々が信頼する CA が署名した」**というところまでです。その証明書の
**主体が何をできるか（権限）は別途決定**しなければなりません。

```java
// 취약(#4): 신뢰된 인증서면 CN 무관하게 전원 ROLE_ADMIN
return User.withUsername(cn).authorities("ROLE_ADMIN").build();

// 안전: 인증서의 Subject DN/SAN을 신원 저장소와 매핑해 실제 권한을 조회
UserDetails u = partnerDirectory.lookupByCertificateSubject(subjectDn); // 없으면 인증 실패
// -> 파트너 A의 서비스 계정은 ch5.read, 배치 계정은 ch5.write 처럼 개별 권한
```

Spring Security の観点では、`x509()` の `subjectPrincipalRegex` で CN/SAN を抽出した
うえで、**その値を実際のディレクトリ（DB/LDAP）とマッピングする `UserDetailsService`**
を接続しなければなりません。lab のように「証明書 = 管理者」と一括りにすると、トラスト
ストアに証明書が1つ追加された瞬間に全員が管理者になります。

## B.3 証明書のライフサイクル — 発行・ローテーション・失効・有効期限

実務の mTLS の半分は証明書の運用です。

- **発行**: 社内 CA（または Vault PKI、cert-manager）でサービス/パートナー別に証明書を
  発行する。
- **ローテーション(rotation)**: 短寿命の証明書を自動更新する（例: SPIFFE/SPIRE は
  数時間単位の SVID を自動ローテーションする）。
- **失効(revocation)**: 流出時に **CRL/OCSP** で無効化する。mTLS でよく漏れる部分 —
  失効確認をしないと、窃取された証明書が有効期限まで有効なままになる。
- **有効期限の監視**: 証明書の期限切れによる障害は、大規模なサービス停止の定番の原因。

## B.4 実務での適用例

- **オープンバンキング/決済**: 英国の OBIE、eIDAS QWAC などは mTLS を必須とする。
  銀行-フィンテック間の API 呼び出しでクライアント証明書によって機関を識別する。
- **サービスメッシュ**: Istio/Linkerd はサイドカー間の通信に**自動 mTLS** を適用し、
  アプリケーションコードを変更せずにサービス間の身元と暗号化を確保する。
- **IoT/デバイス**: デバイスごとに証明書を埋め込み、無断機器の接続を遮断する。
- **ゼロトラスト内部ネットワーク**: 「ネットワーク上の位置」ではなく「証明書の身元」で
  サービス間のアクセスを制御する。

## B.5 よくある落とし穴

- コネクタ全体を `clientAuth=required` で強制し、ヘルスチェック・静的リソースまで証明書
  を要求する（可用性の低下）。→ ch4 のように**特定のパスにのみ** mTLS を適用する
  （optional 検証 + Spring Security フィルタで強制）ほうが柔軟。
- 失効（CRL/OCSP）を確認しない。
- 証明書の身元と権限を分離しない（#4）。
- 秘密鍵をイメージ/リポジトリに含める（→ このプロジェクトも `certs/*.p12,*.pem` を
  `.gitignore` で除外し、実行時に `generate-certs.sh` でローカル生成する）。

## B.6 lab で直接確認

```bash
./certs/generate-certs.sh
MTLS_ENABLED=true mvn spring-boot:run
# 신뢰된 클라이언트 인증서 -> 200

```
